# Migration 0002: campaign persistence

**Status: implemented in the app and tested locally, but not approved for any real database.** `migrations/postgres/0002_campaigns.sql` has been applied only to disposable local test databases. It has not been applied to Supabase or any other real database.

**Changes made while implementing (the file had never been applied anywhere real):**
- a required, fixed campaign `name`;
- a `session_inactive` pause reason;
- manual retry (`failed` or `unresolved` → `pending`), allowed only while the campaign is sending or paused;
- a claim counts its attempt (`attempts` increases with `claim_count`);
- an index for "already sent in an earlier campaign" warnings.

**What the app does on each schema version:**
- **Version 1** (Supabase today): the app runs; campaigns are reported unavailable with an explanation.
- **Version 2:** campaigns are enabled.
- **Anything newer** is refused at startup.

**Approval gate:** `scripts/db-migrate.js` applies files only up to `APPROVED_MIGRATION_VERSION` in `src/store/pgMigrate.js`. That is still **1**, so running the script against Supabase today applies nothing new and reports `0002_campaigns` as "prepared but not approved". Only the PostgreSQL tests apply 0002, and only with an explicit `{ target: 2 }`.

The CSV review stays stateless. A campaign row exists only after an admin explicitly **confirms** a reviewed list. The app side is `src/campaigns.js`, the stores are `src/db.js` and `src/store/postgres.js`, and the shared rules are in `src/store/campaignRules.js`. SQLite has the same schema and rules (schema version 3).

## Tables

### `mailer.campaigns`
One row per confirmed list.

| Column | Purpose / rule |
|---|---|
| `id uuid` PK | Campaign id (generated by the app) |
| `creation_key uuid` **unique** | Sent with the confirmation. Generated by the browser when the review is shown. Repeated or concurrent confirmations with the same key resolve to one campaign. |
| `created_by` → `admins(id)` | Who confirmed. Restrict on delete: history keeps its author. |
| `session_id` → `session_templates(id)` | One of s1–s4 (the FK enforces it) |
| `session_name` | The session's name at confirmation (1–80 characters) |
| `template_version` (> 0), `template_hash` (64 hex) | Exactly what was reviewed: `templateContentHash()` from `src/csvImport.js` |
| `recipients_hash` (64 hex) | The reviewed list's fingerprint (`recipients_hash` from the review) |
| `total_recipients` (1–1000), `csv_rows`, `invalid_rows`, `duplicate_rows`, `blank_rows` | Counts from the review, for audit. They must add up. |
| `status` | `confirmed`, `sending`, `paused`, `completed` or `cancelled` (model below) |
| `stop_reason` | Fixed vocabulary: `admin`, `template_changed`, `provider_rate_limited`, `provider_unavailable`, `sender_not_verified`, `error`. Required when paused. |
| `confirmed_at`, `started_at`, `finished_at`, `updated_at` | Which ones may be set depends on the status (checked) |

**Progress counts are not stored.** Pending, claimed, accepted, failed, skipped, unresolved and so on are counted from `campaign_recipients` (indexed by `campaign_id, status`), so they can never drift from the real rows. Only the totals fixed at confirmation are stored.

**Template content is not copied.** The campaign records the version and content hash. Before each batch, the sender checks the session's current template against both. If either differs, the campaign pauses with `template_changed`, and the list must be reviewed and confirmed again. This avoids a second copy of up to about 700 KB of content per campaign. Snapshotting the content instead is an open question below.

### `mailer.campaign_recipients`
One row per valid recipient of a confirmed campaign.

| Column | Purpose / rule |
|---|---|
| `id bigint identity` PK | |
| `campaign_id` → `campaigns(id)` | Restrict on delete |
| `row_number` (2–5000) | CSV line, for traceability. **Unique per campaign.** |
| `name` | 1–100 characters, trimmed, no control characters, no `{{` or `}}` (mirrors `validateRecipient`) |
| `email` | Normalized: trimmed, lower-case, 3–254 characters, contains `@`, no spaces, `,`, `;`, `<` or `>`. **Unique per campaign.** |
| `people smallint` | Number of people on the invitation: the CSV `people` column, or 1 for `name,email` lists. 1–50, default 1, **fixed after confirmation**, rendered as `{{number_of_people}}`. |
| `send_id uuid` **unique** | Stable Resend `Idempotency-Key` (`tangy-campaign/<send_id>`) for every request for this recipient, including retries |
| `status` | `pending`, `claimed`, `accepted`, `rejected`, `failed`, `unresolved`, `skipped` or `dry_run` (model below) |
| `attempts` (0–10), `claim_count` (0–20) | Provider requests made, and claims taken. `attempts <= claim_count`. Both only increase. |
| `claimed_at`, `next_attempt_at`, `first_attempt_at` | The claim time (required while claimed), the earliest retry time, and the first request time. The first request starts Resend's roughly 24-hour idempotency window. |
| `provider_message_id` | Required when accepted |
| `reason` | Fixed vocabulary only. Never a provider response body, message content or secret. |
| `created_at`, `updated_at`, `completed_at` | `completed_at` is set exactly when the status is final |

**Not stored:** the uploaded CSV, invalid or duplicate rows, rendered messages, and provider responses.

### Unsubscribe and suppression (also in 0002)
These were added to 0002 rather than a new 0003, because 0002 has never been applied anywhere real and campaigns must never be live without unsubscribe support. One migration means no database can be at "campaigns without unsubscribe".

- **`campaign_recipients.unsubscribe_hash`** (64 hex, unique, fixed): SHA-256 of the recipient's unsubscribe token. The token itself is never stored; see `src/unsubscribe.js`.
- **`mailer.suppressions`:**
  - `email_hash` (PK, SHA-256 of the normalized address; no plain text);
  - `reason` (`unsubscribe`, `manual`, `bounce` or `complaint`);
  - `source` (`link`, `one_click`, `admin` or `provider`);
  - `campaign_id` (audit);
  - `created_at`.
- **Runtime grants on `suppressions`:** `SELECT, INSERT` only. Opt-outs are never changed or removed by the app.
- **Row-level security:** the same `mailer_runtime_access` policy as the other tables.
- **`claimed → skipped`** is allowed only with reason `suppressed`: an opt-out noticed right before sending.
 - **Migration checksum:** `people` was added to `0002_campaigns` before applying the current version to the Supabase database checked during preflight (schema version 1; campaign tables absent). This changed the checksum (`2c66965b…` → `360bd697…`). Any database that applied the earlier version will fail the runner's checksum check and requires separate investigation before migration.
- **Index `campaign_recipients_pending_email_idx`:** an opt-out skips pending recipients in every campaign.

**Supabase scripts:**
- before applying: `docs/supabase/03_preflight_0002.sql` (read-only) and `scripts/db-migrate.js --plan` (read-only);
- after applying: `docs/supabase/04_verify_0002.sql` (read-only);
- reference rollback: `docs/supabase/99_rollback_0002.sql`. It's fully commented out, and it would delete the suppression list. Export it first if it was ever used.

## State models (enforced by triggers as well as by the app)

**Campaign**
```
confirmed ─▶ sending ─▶ completed
    │          │  ▲
    │          ▼  │
    │        paused
    ▼          │
cancelled ◀────┘   (also from sending)
```
- `completed` is allowed only when no recipient is `pending` or `claimed`.
- `completed` and `cancelled` are final.
- Every confirmation field (session, version, hashes, counts, author, key, time) is fixed after insert.
- A campaign is always created as `confirmed`.

**Recipient**
- `pending → pending` (reschedule), `claimed`, or `skipped`.
- `claimed → claimed` (the holder recording an attempt, or a take-over of a stale claim with `claim_count + 1`), `pending` (retry later), `accepted`, `rejected`, `failed`, `unresolved` or `dry_run`.
- `unresolved → accepted` or `failed` (manual resolution after checking the Resend dashboard).
- Everything else is final.
- **Claims:** a claim increments `claim_count` by exactly one, and only while the campaign is `sending`.
- **Attempts** rise by one at a time, only while claimed.
- **Fixed fields:** name, email, row, send id and campaign.

**One open campaign per session:** a partial unique index on `session_id` where the status is `confirmed`, `sending` or `paused`. A paused campaign still blocks a new one for that session (cancel it first), so two lists can never go out through one session at once. Completed and cancelled campaigns don't block.

**The list is fixed at confirmation:**
- A deferred constraint trigger requires exactly `total_recipients` rows at commit, so a confirmation is all or nothing.
- A statement trigger refuses recipients for a campaign that is no longer `confirmed`, or beyond its total, so a list can never grow later.

## Constraints, indexes, RLS and grants

- **Primary and foreign keys:**
  - `campaigns.id`, `campaign_recipients.id`;
  - `campaigns.created_by → admins`, `campaigns.session_id → session_templates`, `campaign_recipients.campaign_id → campaigns`.
- **Unique:**
  - `campaigns.creation_key`;
  - `campaign_recipients.send_id`;
  - `(campaign_id, email)`;
  - `(campaign_id, row_number)`;
  - the partial index `campaigns_one_open_per_session`.
- **Indexes:**
  - recipients due for claiming: `(campaign_id, next_attempt_at nulls first, row_number) where status = 'pending'`;
  - stale claims: `(campaign_id, claimed_at) where status = 'claimed'`;
  - progress: `(campaign_id, status)`;
  - campaigns by time;
  - open campaigns by status.
- **Checks:** status vocabularies, the timestamps allowed in each status, reasons that match the status, the counter bounds and the formats above.
- **Triggers:** four plpgsql functions in schema `mailer`, all running with the caller's rights (no `SECURITY DEFINER`), with `search_path` pinned to `pg_catalog, mailer` and `EXECUTE` revoked from `public`.
- **RLS:** enabled on both tables, with one policy, `mailer_runtime_access`, for `mailer_runtime` (the same as 0001).
- **Grants to `mailer_runtime`:** `SELECT, INSERT, UPDATE` on both tables, plus `USAGE` on `campaign_recipients_id_seq`.
  - **No `DELETE` or `TRUNCATE`.** The runtime role also can't disable triggers or RLS, since it doesn't own the tables.
  - Everything is revoked from `public`, `anon` and `authenticated`.
- **Not touched:** 0001's tables, roles and policies, and connection limits. 0001's file is unchanged; its checksum is pinned by a test.

## How the future implementation will use this (not implemented)

1. **Double-clicking Confirm.**
   - Both requests carry the same `creation_key`.
   - The insert is `insert … on conflict (creation_key) do nothing`. The second request finds the existing campaign and returns it, so only one campaign and one recipient set are created.
2. **Two requests confirm the same review.** Same key: as above. A different key for the same session: the open-campaign index rejects the second, and the endpoint reports that a campaign is already open.
3. **The template changes after review.**
   - At confirmation, the server re-reads the saved template. If the version or content hash differs from what the browser reviewed, it refuses and asks for a re-review.
   - While sending, each batch re-checks the version and hash. On a mismatch the campaign pauses with `template_changed`; claimed recipients go back to `pending` with no request made, and nothing changed is sent.
4. **The list changes after review.**
   - Confirmation re-parses the CSV on the server, as the review does, and compares the result with the reviewed `recipients_hash`. Any difference requires a re-review.
   - After confirmation the list is fixed, by the triggers above.
5. **Two workers claim the same recipient.**
   - Claims are a compare-and-swap (`… where status = 'pending' and claim_count = $seen`), or batch claims with `FOR UPDATE SKIP LOCKED`.
   - The trigger also requires `claim_count + 1`. Exactly one worker wins (tested).
6. **A process crashes after claiming.**
   - The row stays `claimed` with `claimed_at`. After a stale window (longer than the provider timeout plus a margin), another worker may take it over (`claim_count + 1`).
   - It resends with the **same** `send_id`, so Resend returns the original result if the first request had been accepted (within the roughly 24-hour key window).
7. **A provider timeout with an unknown result.**
   - The recipient goes back to `pending` with `reason = 'timeout'` and a backed-off `next_attempt_at`, and is retried with the same key.
   - If the outcome is still unknown when the key window would expire (measured from `first_attempt_at`), it becomes `unresolved` instead of being retried. That needs a manual check in Resend.
   - It is never marked failed or sent again with a new key.
8. **Paused while a worker runs.**
   - Pausing updates the campaign row. Claims are refused by the trigger unless the campaign is `sending`, and the claim transaction reads the campaign row `FOR SHARE` first, so a pause waits for that claim transaction to commit and nothing is claimed after it.
   - Requests already in flight (at most one batch) finish and record their outcome. Pausing never interrupts a request.
9. **Cancelled with work pending.**
   - In one transaction: the campaign goes to `cancelled` and its `pending` recipients go to `skipped` (`reason = 'cancelled'`).
   - Claimed in-flight recipients finish and record their outcome. Nothing new can be claimed, because the trigger requires `sending`.
10. **Restart after an application restart.**
    - Nothing lives in memory. A worker, or the open admin page, finds `sending` campaigns with due `pending` recipients and stale `claimed` rows, and continues (case 6).
    - Paused campaigns stay paused until an admin resumes them.

**Provider calls happen outside transactions.**
- A claim is one short transaction (claim, commit).
- Then the Resend request is made with no database connection held.
- Then one short transaction records the outcome.
- No lock is ever held across a network request. This is the same pattern as the single-send `claimSend`/`completeSend`.

**Not exactly-once.** Duplicate protection rests on the database claim plus Resend's idempotency key, which lasts about 24 hours. That gives at-most-once acceptance per key within that window, not a guarantee that holds forever. Unresolved outcomes are surfaced, not retried blindly.

## Suppressions: deferred to the sending/webhook phase
A `suppressions` table is **not** included.
- Without bounce and complaint webhooks or an unsubscribe endpoint, nothing would fill it, and an empty list would look like a safeguard without being one.
- It holds personal data with its own retention rules, which deserve their own review.
- It needs its own grants: probably insert-only for the webhook path, plus a manual entry path.

When added, it should be keyed by normalized email, with a reason (`bounce`, `complaint`, `unsubscribe`, `manual`), a source, and created and expiry timestamps. It would be checked when claiming (`skipped`, `reason = 'suppressed'` is already allowed).

**Privacy:** suppression entries usually must be kept, to honour the opt-out, after other data is deleted. Storing a hash instead of the address is an option, but it makes manual review harder.

## Retention and privacy
- `campaign_recipients` holds names and email addresses. The runtime role can't delete them.
- **Proposal:** an owner-run purge (CLI, like `scripts/admin.js`) that removes recipient rows of campaigns finished more than *N* days ago, keeping campaign-level counts. *N* is a product decision.

## Rollback
- **Before any real campaign exists:** rollback is safe. The SQL below is commented out; it is destructive and should run only after approval, by the owner.
- **After real campaigns exist:** dropping the tables **destroys campaign history and recipient outcomes**. Prefer leaving the tables in place, which is harmless to the current app, and fixing forward with a 0003.
- **The tables are additive.** Older code ignores them, but its strict schema-version check (below) would refuse to start, so a code rollback also needs `EXPECTED_SCHEMA_VERSION` handling.

```sql
-- ⛔ DESTRUCTIVE — owner only, after approval. Deletes all campaign data.
-- begin;
-- drop table if exists mailer.campaign_recipients;
-- drop table if exists mailer.campaigns;
-- drop function if exists mailer.campaigns_guard(), mailer.campaigns_complete_list(),
--   mailer.campaign_recipients_insert_guard(), mailer.campaign_recipients_guard();
-- delete from mailer.schema_migrations where version = 2;
-- commit;
```

## Open questions (product decisions)
1. **Paused campaigns:** should they block a new campaign for the same session (proposed: yes)? Or should "open" mean `sending` only?
2. **Template content:** store the hash and stop on change (proposed), or snapshot the content into the campaign?
3. **SQLite:** decided: campaigns also work on SQLite (schema version 3, same rules), for local dry runs.
4. **Limits:** the retry policy (maximum attempts, currently capped at 10, and the backoff) and the stale-claim window.
5. **Recipient data retention period (*N* days),** and whether campaign-level history is kept indefinitely.
6. **Runner:** who triggers sending on Vercel: the open admin page (batch per request), or a scheduled job?
7. **Cross-campaign duplicates:** should the same address in two different campaigns of the same session be allowed (currently allowed), warned about, or blocked?
